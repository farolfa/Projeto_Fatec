2. Escopo Funcional do Banco

2.1 Dominio de negocio

  • Cadastro e autenticacao de usuarios.
  • Separacao de papeis: cliente e prestador.
  • Catalogo de servicos por categoria.
  • Criacao de pedidos e envio de propostas.
  • Avaliacao, favoritos, notificacoes e suporte.
  • Canal de mensagens entre participantes.

2.2 Entidades principais

  • USUARIO, PRESTADOR, CLIENTE
  • CATEGORIA, SERVICO_CATALOGO, SERVICO_OFERECIDO
  • PEDIDO, PROPOSTA, AVALIACAO
  • ENDERECO, FAVORITO, NOTIFICACAO
  • PARTICIPANTE, MENSAGEM
  • TICKET_SUPORTE, RESPOSTA_TICKET

6. Regras de Integridade

6.1 Integridade de entidade

  • Toda tabela possui PK para unicidade dos registros.
  • Especializacoes (CLIENTE e PRESTADOR) usam PK=FK para garantir identidade com USUARIO.

6.2 Integridade referencial

  • Pedidos, propostas, avaliacoes e mensagens dependem de registros pai.
  • Relacionamentos 1:N sao implementados com FK no lado N.

6.3 Integridade de dominio

  • Campos status e tipo devem operar com valores controlados.
  • Campo nota de AVALIACAO deve respeitar faixa de 1 a 5.

7. Normalizacao (analise didatica)

  • 1FN: atributos atomicos e sem grupos repetitivos nas tabelas principais.
  • 2FN: dependencias parciais minimizadas (chaves simples em quase todas as entidades).
  • 3FN: separacao de conceitos reduz redundancia (ex.: CATEGORIA, SERVICO_CATALOGO e SERVICO_OFERECIDO).

Pontos de atencao academica: FAVORITO e NOTIFICACAO_LIDA_EXTERNA podem evoluir com constraints adicionais para reforcar consistencia e evitar duplicidades logicas.

8. SQL de Referencia (DDL e consultas)

8.1 Exemplo de criacao de tabela

CREATE TABLE usuario (
  id BIGINT PRIMARY KEY,
  nome VARCHAR(120) NOT NULL,
  email VARCHAR(160) NOT NULL UNIQUE,
  cpf VARCHAR(14) NOT NULL UNIQUE,
  tipo VARCHAR(20) NOT NULL,
  status INT,
  ativo BIT NOT NULL
);

8.2 Exemplo de relacionamento

CREATE TABLE pedido (
  id BIGINT PRIMARY KEY,
  id_usuario BIGINT NOT NULL,
  id_servico BIGINT,
  id_endereco BIGINT,
  titulo VARCHAR(160) NOT NULL,
  status VARCHAR(30) NOT NULL,
  CONSTRAINT fk_pedido_usuario FOREIGN KEY (id_usuario) REFERENCES usuario(id)
);

8.3 Consulta com join

SELECT p.id,
       p.titulo,
       u.nome AS cliente,
       sc.titulo AS servico_base
FROM pedido p
JOIN usuario u ON u.id = p.id_usuario
LEFT JOIN servico_catalogo sc ON sc.id = p.id_servico;

9. Administracao do Banco (visao de aula)

9.1 Indices recomendados

  • Indices em todas as FKs para acelerar joins.
  • Indice composto em PROPOSTA(id_pedido, id_prestador).
  • Indice em PEDIDO(status, data_criacao) para filtros operacionais.

9.2 Seguranca e acesso

  • Perfis de acesso separados: leitura, operacao e administracao.
  • Auditoria para alteracoes sensiveis (status, avaliacoes, suporte).
  • Criptografia para dados sensiveis e backup cifrado.

9.3 Backup e recuperacao

  • Politica full semanal + incremental diario.
  • Teste de restore periodico em ambiente homologacao.
  • Definicao de RPO e RTO conforme criticidade do sistema.

10. Conclusao

A modelagem de dados do FazTudoJA apresenta estrutura coerente para o contexto de marketplace de servicos, com entidade central de usuario, especializacoes e fluxo completo de solicitacao-proposta-execucao-avaliacao. O desenho atende bem aos fundamentos de administracao de banco de dados e pode evoluir com refinamentos de constraints, estrategia de indices e politicas de seguranca para cenarios de alta escala.
